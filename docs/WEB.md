# Веб-кабинет «Поток»

Первая версия для просмотра результатов обработки и подготовки проверочных отчётов.
Работает в браузере. Отдельный сервер для интерфейса не требуется: его контейнер
можно добавить к существующей PostgreSQL на том же сервере.

## Что уже работает

- Вход по паролю; роли «Сотрудник» и «Администратор».
- Сотрудник видит только назначенные автобусы. Проверка действует на сервере,
  включая журнал событий, формирование и повторное скачивание отчётов.
- Обзор входов/выходов, график по дням, фильтры периода, автобуса и назначения данных.
- Журнал учтённых и исключённых событий с причиной исключения.
- Проверочный CSV: UTF-8 с BOM, разделитель `;`, фиксированный снимок результата
  с контрольной суммой SHA-256. История собственных отчётов доступна сотруднику,
  история всех отчётов — администратору. Отзыв доступа закрывает старые скачивания.
- Администратор создаёт пользователей, назначает автобусы, отключает учётные записи
  и просматривает журнал действий. Регистрация посетителями отключена.
- Рабочие, тестовые и непроверенные автобусы обозначаются отдельно.
- Раздел «Видеозаписи»: загрузка нескольких MP4 по очереди с паузой и докачкой,
  привязкой к автобусу и камере, проверкой контейнера видео и лимитом места.
- Карточка каждой записи и скачивание её результата CSV после завершения;
  итог файла сохраняется независимо от перехода календарного дня.

После загрузки запись автоматически ставится в очередь. Отдельная служба
распределяет задания между процессами с ограничением CPU/RAM и продолжением
после сбоя. В кабинете видны этапы и прогресс; процент загрузки файла отличается
от прогресса подсчёта. [Установка службы обработки](ARCHIVE_QUEUE.md).
Он не подключён к 1С: конфигурация и формат обмена заказчика пока неизвестны.
CSV предназначен для проверки, совместимость с импортом 1С не заявлена.
Кадры, изображения людей и признаки распознавания через кабинет не передаются.

## Быстро посмотреть локально, без PostgreSQL

Демостенд включён в полную версию проекта. В чистой серверной поставке его
генератор и команда `run_web_demo` отсутствуют; там используйте раздел установки ниже.

В PowerShell из корня проекта, используя существующее окружение:

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements-web.txt
.\venv\Scripts\python.exe -m tools.run_web_demo
```

Откройте [локальный кабинет](http://127.0.0.1:8000/). Терминал покажет логины
`demo-admin`, `demo-employee` и сгенерированный пароль. При занятом порте:
`python -m tools.run_web_demo --port 8001`. Остановка — `Ctrl+C`.

Здесь **все цифры вымышлены** и отмечены в интерфейсе. Команда использует только
`.local/web-demo/`: отдельные SQLite-файлы с демонстрационными результатами,
пользователями и историей отчётов. Повторный запуск восстанавливает демонстрационную
статистику и пароли двух демонстрационных пользователей. Пароль сохраняется в
`.local/web-demo/demo-access.json`, который исключён из Git. Рабочая БД не открывается.
Для Linux замените путь интерпретатора на `.venv/bin/python`.

## Подключение к настоящим результатам на сервере

Это инструкция установки, **автоматического развёртывания на вашем сервере не было**.
Нужна версия исходников с файлами `Dockerfile.web` и `docker-compose.web.yml`.
Старая поставка от 14 ноября их не содержит. Перед установкой сохраните конфигурацию
и сделайте резервные копии данных. Не переключайте ветку внутри каталога работающего
теста вслепую; сначала проверьте состав обновления.

Команды ниже выполняются по SSH в каталоге существующего Compose-проекта.
Имя Compose-проекта должно оставаться прежним, иначе будут выбраны другие сеть и тома.

```bash
python3 -m tools.setup_web_env
docker compose -f docker-compose.yml -f docker-compose.web.yml build web
docker compose -f docker-compose.yml -f docker-compose.web.yml run --rm --no-deps web_setup
docker compose -f docker-compose.yml -f docker-compose.web.yml up -d --no-deps web
docker compose -f docker-compose.yml -f docker-compose.web.yml exec web python manage_web.py createsuperuser
```

Последняя команда интерактивно запросит логин и пароль администратора. Постоянного
пароля по умолчанию нет. При добавлении сотрудников используйте индивидуальные пароли.
`web_setup` требует уже созданных таблиц счётчика и работающей PostgreSQL.
Существующие видео-контейнеры и PostgreSQL этими командами не пересоздаются.
Не используйте `docker compose down -v`: это удалит тома.

На **своём компьютере** откройте второй терминал и запустите:

```powershell
ssh -N -L 8000:127.0.0.1:8000 root@АДРЕС_СЕРВЕРА
```

Пока это соединение открыто, кабинет доступен в браузере компьютера по адресу
[http://127.0.0.1:8000/](http://127.0.0.1:8000/). Внешний порт 8000 не открывается:
Compose привязывает его только к `127.0.0.1` сервера. Ноутбук можно выключить —
обработка и веб-сервис на сервере продолжат работу; при следующем просмотре создайте
SSH-туннель заново.

В разделе «Автобусы» заведите идентификаторы, **точно совпадающие с `BUS_ID`**
обработчиков, затем назначьте их сотрудникам. Это справочник доступа, он не меняет
конфигурацию обработчиков. Администратор видит и незарегистрированные результаты.
Без назначений сотрудник не видит статистику. Неразмеченные `TEST_*` считаются
тестовыми, остальные неизвестные идентификаторы — непроверенными; явная карточка
автобуса имеет приоритет. Код внешней системы пока только сохраняется в справочнике.

### Конфигурация и права БД

`python -m tools.setup_web_env` создаёт отдельный приватный `.env.web` с двумя
случайными секретами. Файл `.env` обработчиков не изменяется.
Для нестандартных имени БД, часового пояса или параметров подключения исправьте
соответствующие `WEB_*` в `.env.web`; шаблон — `web.env.example`.
`WEB_TIMEZONE` должен совпадать с бизнес-часовым поясом счётчика.

Одноразовый `web_setup` получает административное подключение из `.env` и создаёт
отдельного пользователя PostgreSQL `bus_dashboard` с `SELECT` на таблицы событий
и суточных итогов. Он не меняет схему и пассажирские данные. Существующая чужая
роль не перезаписывается. Пароль должен быть отдельным, не паролем обработчика.
Постоянный контейнер `web` получает **только `.env.web`** и не знает пароль владельца БД.
Чтение ограничено трёхсекундным тайм-аутом. Таблица `counter_runtime_state`
кабинету недоступна; большие снимки памяти распознавания не запрашиваются.

### Где что хранится

- PostgreSQL: существующие события и статистика счётчика; кабинет их только читает.
- Том `web_state`: SQLite `accounts.sqlite3` с пользователями, правами, сессиями,
  журналом действий и снимками CSV. Отдельно от служебного SQLite-журнала счётчика.
- Том `video_uploads`: приватные записи и незавершённые части; не публикуется
  как MEDIA_URL и не доступен для скачивания без авторизации через веб-сервер.
  В контейнере web это `/app/uploads`, в новом обработчике с web overlay —
  `/app/data/uploads` только для чтения. У работающего старого контейнера новый
  том сам не появится: используйте overlay при создании следующего обработчика.
- Статика: локальная, без внешних CDN, шрифтов и аналитики.

SQLite выбран для первого экземпляра кабинета с небольшой нагрузкой. Несколько
веб-реплик и масштабирование на большой парк потребуют переноса служебных таблиц
кабинета в отдельную PostgreSQL-БД и проектирования очереди обработки.
Это не система диспетчеризации 1500 камер.

Для резервного копирования `web_state` на короткое время остановите **только web**,
сохраните его том и `.env.web` в защищённое хранилище и запустите web снова.
Копирование открытого SQLite обычным копированием файла не гарантирует целостность.
Резервные копии PostgreSQL и журналов обработчиков остаются отдельной задачей.

### Работа и диагностика

```bash
docker compose -f docker-compose.yml -f docker-compose.web.yml ps web
docker compose -f docker-compose.yml -f docker-compose.web.yml logs --tail 50 web
docker compose -f docker-compose.yml -f docker-compose.web.yml restart web
```

Web ограничен 0,5 CPU и 384 МБ RAM, один процесс и два потока. Это ограничения
контейнера, не подтверждённый расход под многопользовательской нагрузкой.
`/health/` проверяет доступность web-процесса, **не состояние камер или PostgreSQL**.
Обновление показателей — после загрузки/обновления страницы, автоматического polling нет.
Время «обновлено» относится к статистике, а не к heartbeat камеры.
Ошибка подключения отображается явно, без подмены показателей нулями.

Для публичного сайта используйте отдельную HTTPS-конфигурацию ниже. Она задаёт
точный `WEB_ALLOWED_HOSTS`, HTTPS origin для CSRF, защищённые cookies и доверие
заголовку HTTPS от собственного прокси. PostgreSQL и Docker API наружу не открываются.

## Загрузка видеозаписей

Войдите в кабинет, откройте «Видеозаписи», выберите автобус, код камеры и MP4.
Можно выбрать несколько файлов: они отправляются последовательно. Кнопка
«Приостановить» сохраняет принятые части. После обрыва или закрытия вкладки выберите
те же записи, автобус и камеру и нажмите «Загрузить видео». Новый вход в кабинет
не удаляет незавершённую загрузку. Для отмены в списке есть отдельная кнопка.

Сотрудник видит свои загрузки для назначенных автобусов, администратор — все.
Отзыв назначения закрывает и продолжение загрузки. Завершённая запись не удаляется
кнопкой отмены. Повторный выбор того же имени, размера и отпечатка в том же автобусе
и камере возвращает уже существующую запись, а не создаёт копию.

Файлы отправляются частями до 4 МиБ. Каждый подтверждённый блок записывается на
диск до сохранения позиции в БД. Повтор той же части после потерянного ответа
проверяется по сохранённым байтам; пропуск позиции и несовпадение части отклоняются.
Незавершённый файл имеет расширение `.part`; после проверки `ffprobe` он атомарно
переименовывается в `<UUID>.mp4`. Проверяются наличие видеопотока, размеры и
положительная длительность. Это проверка контейнера, не полное декодирование
всех кадров и не проверка качества экранных часов.

Для докачки сравниваются имя, размер и SHA-256 первого и последнего МиБ; отпечаток
повторно проверяется сервером. Это не полная контрольная сумма всего видео.
Не редактируйте файл во время загрузки и не заменяйте его изменённой копией.
WebCrypto требует HTTPS или `localhost`; через существующий SSH-туннель на
`http://127.0.0.1:8000` загрузка также работает.

По умолчанию: до 20 ГиБ на файл, до 40 ГиБ суммарных резервирований и готовых
записей, минимум 2 ГиБ свободного места, до трёх незавершённых загрузок на пользователя.
Параметры `WEB_UPLOAD_MAX_GB`, `WEB_UPLOAD_QUOTA_GB`, `WEB_UPLOAD_MIN_FREE_GB`,
`WEB_UPLOAD_MAX_ACTIVE` задаются в `.env.web`. Лимиты относятся к отдельному
хранилищу загрузок; старые видео в `./data` учитываются проверкой свободного места,
если находятся на том же файловом разделе. Просроченные части сами не удаляются:
пользователь или администратор может отменить их в списке. Завершённые записи
нужно архивировать по согласованной политике хранения; веб-кнопки удаления их нет.

При локальном запуске нужен `ffprobe` из FFmpeg в PATH либо `WEB_FFPROBE` с полным
путём к исполняемому файлу. Серверный `Dockerfile.web` устанавливает его сам.
Локальный каталог по умолчанию — `data/uploads`; переопределение — `WEB_UPLOAD_DIR`.
Демостенд использует отдельный каталог внутри `.local/web-demo/`.

Метаданные загрузки и очередь находятся в служебной SQLite кабинета. HTTP-запрос
не выполняет подсчёт и не меняет пассажирские события PostgreSQL: это делает
отдельный обработчик. Для восстановления сохраняйте `web_state`, `video_uploads`,
`archive_state` и PostgreSQL в согласованной точке. Служба сама готовит карту часов
для нового файла и выделяет отдельное состояние. При неоднозначных часах запись
ожидает проверки; переносить карту другого исходного файла нельзя.

Для обновления существующей установки, сохраняя работающие обработчики:

```bash
docker compose -f docker-compose.yml -f docker-compose.web.yml build web
docker compose -f docker-compose.yml -f docker-compose.web.yml up -d --no-deps web
```

Миграции выполняются командой web при старте. Для автоматической обработки нужно
также установить `archive_scheduler` по инструкции очереди. Эти две команды
не перезапускают контейнеры обработки. Если установка уже использует HTTPS,
включайте и `-f docker-compose.https.yml` с прежним `WEB_DOMAIN` в обе команды.

## Домен и HTTPS без SSH-туннеля

Достаточно существующего сервера и публичного IP. Отдельный хостинг для сайта
покупать не требуется. Домен оплачивается отдельно у регистратора.

1. Создайте A-запись, например `panel.example.ru`, с публичным IPv4 сервера.
   AAAA добавляйте только при работающем публичном IPv6.
2. Разрешите входящие TCP 80/443 в сетевом экране провайдера и ОС. SSH остаётся
   для администрирования; порт 8000 и порт PostgreSQL не публикуются.
3. Добавьте в серверный `.env` строку `WEB_DOMAIN=panel.example.ru` (без схемы,
   пути и порта). Имена в примере нужно заменить вашим реальным доменом.
4. После обновления исходников запустите только web и HTTPS-прокси:

```bash
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.https.yml build web
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.https.yml up -d --no-deps web
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.https.yml up -d --no-deps caddy
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.https.yml logs --tail 50 caddy
```

Существующая настройка `.env.web`, роли БД и аккаунта администратора требуется
как в разделе первой установки. Caddy хранит сертификаты в отдельном постоянном
томе, автоматически получает/обновляет их и перенаправляет HTTP на HTTPS.
Не останавливайте существующие видео-контейнеры для установки прокси.
Если 80/443 уже заняты другим веб-сервером, подключите кабинет к его HTTPS-прокси,
а не запускайте второй на тех же портах. При последующих обновлениях сохраняйте
HTTPS overlay, иначе web вернётся к локальным настройкам cookies и HTTPS.

После настройки сайт открывается как `https://panel.example.ru` с любого
компьютера без терминала. Вход по логину и паролю остаётся обязательным.
Покупка домена сама по себе не настраивает DNS, HTTPS или публичную доступность.
Конфигурация включена в репозиторий, но на вашем арендованном сервере автоматически
не развёртывалась. Основание настроек: [Caddy HTTPS](https://caddyserver.com/docs/automatic-https)
и [ограничение тела запроса](https://caddyserver.com/docs/caddyfile/directives/request_body).

## Как понимать цифры

Учтённые входы и выходы — результат текущего алгоритма с часовым исключением
повторов каждого направления. Это не число уникальных людей за сутки. Разность
входов и выходов не является надёжной оценкой людей в салоне.
Отчёт суммирует камеры одного автобуса; для нескольких дверей нужно отдельно
проверить пересечения зон камер и отсутствие двойного подсчёта.

Для отчётов используется `current_day_passenger_traffic`: несмотря на название,
в ней сохраняются строки прошлых дней. Если вручную очищать эту таблицу, история
в кабинете станет неполной. Исправление расхождений и ручные корректировки пока
не реализованы. Сохранённый CSV остаётся снимком на момент создания, а не гарантией
того, что обработка видео к этому моменту завершена.

## Проверки

```bash
python -m tools.setup_web_env
# В отдельном тестовом процессе задать WEB_DEMO=1, затем:
python manage_web.py test web.portal.verification web.portal.upload_verification web.portal.job_verification --noinput
python manage_web.py makemigrations --check --dry-run
```

Изолированные проверки: разделение прав, подмена автобуса, чужие отчёты,
отзыв доступа, отключение пользователя, CSRF, ограничение попыток входа,
экранирование HTML/CSV, контрольная сумма, недоступность БД и отсутствие запросов
к памяти распознавания. Дополнительно `tests.test_web_database` проверяет права
реальной временной PostgreSQL; его `TEST_DB_PORT` должен указывать **только на
одноразовую тестовую БД** с учётными данными из существующего протокола тестов.
Демонстрационная SQLite не доказывает права PostgreSQL — это отдельная проверка.

Визуально проверяются страницы входа, обзора, отчётов и ролей, а также мобильное меню.
Модель подсчёта и текущие серверные запуски при разработке кабинета не меняются.

42 веб-теста пройдены: прежние 25 и 17 проверок загрузки, прав на записи,
докачки, повторной части, неверной позиции, исчерпания квоты, повреждённого файла,

Собран и запущен `Dockerfile.web` с неизменяемой корневой файловой системой,
постоянными томами и лимитами 384 МБ / 0,5 CPU. Через браузер загружен настоящий

пересоздан с теми же томами, выполнены повторный вход, докачка и завершение с
настоящим `ffprobe`. Сохранённый файл совпал с исходным по SHA-256. Повтор части
