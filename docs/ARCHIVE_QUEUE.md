# Автоматическая очередь видеоархива

Проверенная загрузка MP4 автоматически создаёт одно задание. Отдельная служба
`archive_scheduler` ожидает записи и запускает свободные процессы обработки.
После загрузки вкладку и ноутбук можно закрыть. При пустой очереди модели не
загружены; диспетчер проверяет задания раз в пять секунд.

## Что происходит с записью

1. Завершение загрузки и создание задания сохраняются в одной транзакции SQLite.
   Незавершённые `.part` в очередь не попадают. Повтор завершения не создаёт копию.
2. Диспетчер выбирает доступное задание по времени постановки. Записи одной пары
   автобус/камера выполняются последовательно; другие камеры могут идти параллельно.
3. Обработчик проверяет настройки и SHA-256 моделей, затем готовит экранное время.
   В `data/*.clock.json` можно держать ранее проверенные карты: они переиспользуются
   только после совпадения SHA-256 всего видео, модели часов, ROI и часового пояса.
   Для нового файла карта строится автоматически тем же инструментом подготовки.
4. Если часы не читаются или склейка требует ручной проверки, задание получает
   «Требуется проверка». Подмена времени серверными часами и автоматическое
   подтверждение неоднозначных переходов запрещены. Другие записи продолжают работу.
5. Подсчёт использует рабочий профиль `test2`, отдельные карту и SQLite-состояние
   для каждого задания. Память людей между независимыми файлами не переносится.
   Часовое исключение повторов использует время камеры.
6. Статус «Завершено» появляется после EOF и успешной доставки конечного состояния
   и событий в PostgreSQL. Окончание декодирования при недоступной БД недостаточно.

В разделе «Видеозаписи» видны очередь, этап подготовки часов, прогресс подсчёта,
входы/выходы, завершение и причина проблемы. Состояние обновляется раз в 10 секунд,
когда вкладка видима. До подтверждённой доставки прогресс ограничен 99%.
Сотрудник видит только свои записи назначенных автобусов. Повторная постановка
после ошибки/проверки доступна администратору и сохраняет контрольную точку.
Завершённую или выполняющуюся запись эта кнопка повторно не запускает.

Нажатие на имя файла открывает отдельную карточку. После завершения доступен
CSV именно этой записи. Накопленные итоги файла сохраняются атомарно вместе
с курсором и outbox и не сбрасываются в полночь; дневные итоги PostgreSQL остаются
разделёнными по дням. Старое состояние без итогов записи через полночь не выдаётся
за полный результат: оно требует отдельной проверки администратора.

## Ресурсы одного сервера

Для тестового сервера 4 vCPU / 8 ГБ RAM стартовые настройки:

```ini
ARCHIVE_CPU_BUDGET=3
ARCHIVE_POOL_MEMORY=4g
ARCHIVE_MAX_WORKERS=2
ARCHIVE_THREADS_PER_WORKER=1
ARCHIVE_MEMORY_PER_WORKER_MB=1400
ARCHIVE_DETECTOR_BACKEND=onnx
```

Эти параметры добавляются в серверный `.env`. Они не являются замером нужной
памяти для всех записей. Контейнер получает общий жёсткий лимит 3 CPU и 4 ГБ,
оставляя часть сервера для web, PostgreSQL и ОС. Число процессов ограничено
одновременно максимумом workers, бюджетом CPU и оценкой памяти на процесс.
Начальные процессы резервируют память до фактической загрузки моделей.

На Linux учитываются CPU quota/cpuset и доступная RAM в cgroup v2, свободная
память хоста и текущий RSS процессов. Возвращаемый файловый кеш учитывается
отдельно от занятой рабочей памяти. Перед новым запуском оценивается свободное
процессорное время; при нехватке CPU или RAM запись ждёт. Уже работающий процесс
не вытесняется ради нового задания. Внутренние потоки детектора/ReID ограничены;
общую фактическую нагрузку всех библиотек сдерживает лимит контейнера.

Диспетчер не останавливает посторонние контейнеры и не знает их будущую нагрузку.
Если старые ручные прогоны ещё работают, учитывайте их при выборе бюджета или
завершите их перед сравнением. При OOM обработчика сохранённая контрольная точка
используется при повторе; повторяющийся OOM требует уменьшить число workers либо
увеличить память. Не меняйте пороги подсчёта или веса ради выделения ресурсов.

Это один узел и одна служебная SQLite, **не кластер для 1700 пятичасовых файлов
в сутки**. Несколько диспетчеров на один кабинет запрещены: файловая блокировка
в `web_state` не позволяет случайно запустить вторую копию. Для нескольких узлов
потребуются отдельная очередь/служебная PostgreSQL и общий планировщик ресурсов.

## Установка и обновление

Сначала установите web, настройте его аккаунт и роль чтения PostgreSQL по
[инструкции кабинета](WEB.md). Сохраните прежнее имя Compose-проекта и постоянные
тома. Приведённые команды не перезапускают ручные видео-контейнеры.

```bash
# Базовый образ вычислений и отдельный образ диспетчера.
docker build -t bus-passenger-counter:archive-base .
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.archive.yml build web archive_scheduler

# Сначала web применяет миграцию очереди.
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.archive.yml up -d --no-deps web
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.archive.yml up -d archive_scheduler

docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.archive.yml logs --tail 50 archive_scheduler
```

При публичном домене добавляйте `-f docker-compose.https.yml` после этих файлов
во **все** команды, чтобы сохранить настройки HTTPS web. `WEB_DOMAIN` остаётся
в `.env`. Caddy при обновлении очереди пересоздавать не нужно.

Образ диспетчера устанавливает web-зависимости поверх вычислительного образа,
но модели загружаются только в дочерних обработчиках. Web не получает пароль
владельца PostgreSQL, Docker socket или права запускать команды от посетителей.
Диспетчер получает `.env` для записи результатов и `.env.web` для своей SQLite.
Пользователь выбирает автобус/камеру, а пути, команды и профиль формирует сервер.

Вариант OpenVINO включается явно до сборки и запуска:

```ini
ARCHIVE_INSTALL_OPENVINO=1
ARCHIVE_DETECTOR_BACKEND=openvino
```

После этого пересоберите `archive_scheduler`. ReID и жилетка остаются ONNX.
Не переключайте backend у уже начатого задания: снимок настроек остановит такое
продолжение для проверки. Сначала закончите начатую очередь на прежнем backend.
Сборка и конфигурация OpenVINO предусмотрены; проведённый интеграционный прогон
этой очереди использовал ONNX.

## Перезапуск и восстановление

```bash
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.archive.yml stop archive_scheduler
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.archive.yml up -d archive_scheduler
```

При остановке диспетчер посылает SIGTERM детям и даёт до 45 секунд на завершение.
Счётчик сохраняет курсор, личности, часовые таймеры и outbox. При жёстком убийстве
восстановится последняя целая контрольная точка. Нельзя использовать `down -v`.

После запуска незавершённые задания возвращаются в очередь. Повтор использует
то же состояние, не начинает подсчёт с пустой памяти. Доставка событий
идемпотентна; конечный checkpoint не опережает доставленные события. Повторная
инициализация PostgreSQL сериализована транзакционной advisory-блокировкой.

Каждая попытка имеет новый token. Старые сообщения не меняют новую попытку.
В течение всей попытки удерживается отдельная файловая блокировка задания.
Если диспетчер погиб отдельно от дочернего процесса, lease перестаёт обновляться:
watchdog останавливает осиротевший процесс. Второй процесс не получит его файловую
блокировку одновременно. Срок lease измеряется монотонными часами узла.

Ошибки запуска и временные сбои повторяются с задержкой 30–300 секунд, максимум
три ошибочные попытки по умолчанию (`ARCHIVE_MAX_ATTEMPTS`). Штатные остановки не
расходуют этот лимит. После исправления причины администратор нажимает «Повторить
обработку». Состояние и события при этом не удаляются. Изменение моделей или
смысловых настроек начатого задания требует отдельной проверки; CPU threads
можно менять без сброса подсчёта.

Для зависших процессов есть отдельный контроль прогресса: по умолчанию 300 секунд
без обновления на этапе подсчёта/сохранения и 7200 секунд на подготовку часов.
Пределы задаются `ARCHIVE_STALL_TIMEOUT_SEC` и `ARCHIVE_CLOCK_TIMEOUT_SEC` в `.env`.
Диспетчер сначала просит процесс завершиться, затем при продолжающемся отсутствии
прогресса принудительно останавливает его. Такое зависание расходует лимит ошибок.
Зависшие неподтверждённые захваты задания также возвращаются в очередь.

## Проверка экранного времени

UUID загрузки и номер задания видны администратору. Файлы задания находятся в
`/app/state/jobs/<номер>/`. Для неоднозначной карты получите обзорные листы:

```bash
docker compose -f docker-compose.yml -f docker-compose.web.yml -f docker-compose.archive.yml exec archive_scheduler \
  python -m tools.review_clock_map --source /app/uploads/UUID.mp4 \
  --map /app/state/jobs/НОМЕР/clock.json --output /app/state/jobs/НОМЕР/clock-review
```

Проверяйте исходные переходы по существующей процедуре. `--accept-transitions`
разрешён только после реального просмотра: он подтверждает отсутствие прохода
пассажира в исключаемом синтетическом переходе. Нельзя ставить его для всей
очереди автоматически. Если карта вообще не построилась, сначала исправьте ROI,
читаемость или подготовьте достоверную карту для этого исходника.

После исправления карты повторная постановка продолжит задание. Если карта
меняется после уже выполненной части подсчёта, проверка fingerprint состояния
не позволит незаметно смешать две временные шкалы.

## Хранение и диагностика

- `web_state`: аккаунты, загрузки, очередь, позиции/состояния задач и heartbeat.
- `video_uploads`: исходные MP4, доступные обработчикам только для чтения.
- `archive_state`: отдельные карты часов, OCR-кеш, checkpoint/outbox, рецепты
  с хешами моделей и журналы попыток. Пароль БД в рецепты не записывается.
- `pgdata`: события, суточные итоги и резервные checkpoint.

Для согласованной резервной копии остановите загрузки/web и диспетчер, затем
сохраните соответствующие тома и PostgreSQL. Рецепты, кеши, журналы и контрольные
точки не публикуются в Git. Автоматического удаления исходников или состояний нет;
планируйте срок хранения и свободный диск. HTTP-загрузка проверяет запас места,
но OCR-кеш и состояния тоже требуют отдельного запаса на вычислительном томе.

## Проверка реализации, 22 ноября 2026

Проверены права и очередь в изолированных Django-БД, CPU/RAM admission, блокировки
процессов и lease, устаревшие сообщения, ограничение повторов, зависший процесс,
отзыв доступа, запрет повторного запуска завершённого задания и предел 99% до
сохранения. Полный набор обычных тестов также использовал отдельную одноразовую
PostgreSQL; проверка параллельного первого создания таблиц запускает четыре клиента
одновременно в новом изолированном SQL schema.

Пройдено 57 веб-тестов. Общий набор: 234 теста без ошибок, 12 предусмотренных
пропусков приватных/необязательных сценариев. Проверены миграции, Compose с web,
HTTPS и очередью, синтаксис JavaScript, серверная упаковка и сборка обоих образов.

В Docker с read-only root, лимитом 2 CPU / 4 ГБ и двумя workers:

- Два процесса одновременно обрабатывали разные камеры; ограничение одной камеры
  отдельно проверено тестом очереди.
- Диспетчер остановлен во время подсчёта; сохранены курсоры 177 и 176 из 300.
  После запуска восстановлены checkpoint и обе записи дошли до EOF.
- Для короткого фрагмента исходной записи автоматически построена карта часов
  (один сегмент, четыре OCR-наблюдения), найден один IN, события и итог записаны
  в отдельную PostgreSQL. Модель и профиль не подменялись тестовым счётчиком.
- Имитирована потеря подтверждения очереди после уже доставленного конечного
  checkpoint: повтор завершился без добавления событий. В БД остались один IN
  и одно событие.
- Отдельный MP4 без читаемых часов получил «Требуется проверка», а не подсчёт
  по времени сервера. Остальные задания завершились.

Итого в интеграционной очереди: шесть записей, пять завершены, одна ожидает
проверки. Статусы, результат и причина проверки просмотрены через кабинет.
Это функциональная проверка на коротких записях, не нагрузочный тест суток архива
и не новая оценка точности детектора. Арендованный сервер автоматически не обновлялся.
