# Обработка суточного архива: предложение архитектуры

Состояние: проект решения, не реализованный планировщик. Дата: 15 ноября 2026.
Рабочая программа и сервер при подготовке этого документа не изменялись.

**Исторический проект; масштабирование отложено.** Текст ниже фиксирует предложение
до архивных изменений 15–16 ноября. Карты часов и атомарные блоки сохранения уже
реализованы в текущей программе; очередь, пул узлов и веб-загрузка остаются планом.
Актуальная эксплуатация: [архивный режим](ARCHIVE_PROCESSING.md),
[CPU-эксперименты](CPU_OPTIMIZATION.md). Приведённые ниже мощности — расчётные
сценарии, не измерение и не конфигурация для покупки.

## Подтверждённые условия

- Около 1700 файлов ежедневно, каждый длительностью около пяти часов видеоряда.
- В одном файле содержится полный рабочий день. Личности между файлами переносить
  не требуется: новый файл начинает отдельную память распознавания.
- Партию нужно обработать за сутки. Для расчёта ниже приняты 24 часа доступного
  вычислительного времени; срок нужно связать с моментом полной доставки файлов.
- Повторы IN и OUT подавляются по прежнему правилу внутри одного файла, с часовым
  интервалом по времени камеры. Между сменами этого связывания нет.
- На видео есть дата и часы камеры. В имеющейся записи вырезаны промежутки.

Следствие: разные файлы могут обрабатываться независимо и в любом порядке.
Состояние одного файла всё равно должно идти в порядке кадров. Разделять его
на независимые куски с обнулением ID нельзя без отдельного алгоритма объединения.

## Масштаб задачи

1700 × 5 = **8500 часов видео в сутки**. Минимальная суммарная скорость —
**354,17 часа видео за один час работы**. При условных 25 кадрах/с это 765 миллионов
исходных кадров в сутки, в среднем **8854 кадра/с** по всей системе.

Если планировать 75% полезной загрузки, требуется 472,22 часа видео за час,
или примерно 11 806 исходных кадров/с при тех же 25 FPS. Коэффициент 75% —
плановый запас, а не измеренное свойство системы.

Условные примеры с этим запасом:

- измеренный узел даёт 1× реального времени: нужно 473 таких узла;
- даёт 5×: 95 узлов;
- даёт 10×: 48 узлов;
- даёт 20×: 24 узла.

Это формула мощности, **не число GPU для покупки**. «Узел» означает весь замеренный
вычислительный комплект с выбранным параллелизмом. Несколько процессов на одной
видеокарте не являются несколькими независимыми узлами. Производительность GPU,
OCR, декодирования и полного подсчёта нужно измерить вместе. В расчёте используется
длительность файла по кадрам/PTS, а не более длинная смена на часах смонтированной записи.

Если весь архив становится доступен только за восемь часов до дедлайна, расчёт
проводится на восемь часов, а не на 24. Если приходят новые 8500 часов ежедневно,
вчерашний недообработанный объём добавляется к сегодняшнему.

## Варианты вычислительной части

**Один CPU-сервер.** Подходит для проверки загрузки, очереди и качества на малой
выборке. Для всего ежедневного объёма производительность текущего прогона слишком
мала. Создание 1700 потоков на нём не увеличит число доступных ядер.

**Пул GPU-workers — основной кандидат.** Несколько подготовленных узлов получают
файлы из общей очереди. Детектор и ReID работают на GPU, декодирование/OCR/БД
распределены по подходящим ресурсам. Начать с одного GPU для измерений, затем
подбирать количество узлов по фактическим часам видео за час и стоимости этой работы.

На каждом GPU нужно отдельно подобрать число одновременно обслуживаемых файлов.
Модели желательно загружать один раз на обслуживающий процесс/устройство,
а не держать 1700 копий. Динамический batch можно формировать из кадров разных
файлов для независимого нейросетевого инференса. Сопровождение людей и часовая
память остаются отдельными для каждого файла; результаты возвращаются в порядке кадров.

**Разделённый конвейер.** При дальнейшем росте отдельно масштабируются загрузка,
декодирование/время, GPU-инференс и последовательный подсчёт. Нейросетевые выходы
можно вычислять параллельно, затем упорядочивать перед трекером. Этот вариант
сложнее и требует ограничения промежуточных буферов и места на диске. Его следует
вводить после измерения, а не сразу заменять им простой worker на файл.

Батчинг и экспорт в TensorRT/FP16 — кандидаты на тестирование. Они не дают
гарантированного множителя скорости. FP16/INT8 могут изменить оценки и сходство
ReID: после них повторяются проверки счётчика и ID. INT8 требует своей калибровки.

## Оптимизации, которые полезны именно архиву

1. Внести уже проверенное устранение повторной отправки состояния и лишнего
   преобразования признаков. Его измерения относятся к сохранению, не ко всему видео.
2. Ввести отдельный режим архивного checkpoint: период по затраченному времени
   обработки, например 30–120 секунд как стартовый диапазон испытаний. Часовое
   правило использует время камеры, а период резервного сохранения — часы сервера.
   Не создавать большой снимок каждую секунду ускоренно обрабатываемого видео.
3. Сохранять согласованный блок «курсор + память ID + события этого блока».
   После сбоя переобработать последний незавершённый блок из исходного файла.
   Для архива это допустимый обмен дополнительной работы на меньшую нагрузку записи.
   Нынешняя программа сохраняет каждый event немедленно; этот архивный режим ещё
   нужно реализовать и проверить, а не включать несуществующим флагом.
4. Хранить тяжёлое состояние в локальном быстром хранилище с резервной копией
   в общем хранилище; в PostgreSQL — задания, версии, компактный прогресс и итоги.
   Протокол должен выдерживать потерю узла и повтор работы от более старого снимка.
5. Обрабатывать только нужную область двери, аккуратно исключив прочие зоны.
   Координаты и пересечение людей проверяются на новой выборке.
6. Проверить вычисление детектора на 10–15 FPS и адаптивный режим на пустых сценах.
   Это эксперимент, не безопасное значение по умолчанию: короткий проход между
   редкими кадрами иначе будет пропущен. Движение двери, свет и перекрытия должны
   входить в проверку. Остальные кадры по-прежнему могут требоваться декодеру.
7. Пересчитывать признаки ReID избирательно только после проверки сохранения ID:
   при новом человеке, сближении/перекрытии и у линии прохода признаки особенно важны.
   Простой пропуск вычисления признаков на каждом N-м кадре может ухудшить связь людей.
8. Распознавать небольшую область часов, а не запускать OCR по целому изображению
   на каждом кадре. Не сохранять отрисованное видео с боксами в штатном режиме.

Цель испытания — максимальные часы видео за час при сохранении согласованной
точности, а не максимальный FPS одного детектора на пустых кадрах.

## Часовая память и время в левом верхнем углу

**Сохранить правило часа можно.** OCR восстанавливает время событий, ReID связывает
человека. Дата и часы сами человека не идентифицируют и не исправляют смену ID.

Порядок получения времени:

1. Предпочесть исходные временные метки регистратора или сопроводительный файл,
   если они содержат реальное время кадров и не потеряны при монтаже.
2. Если есть только надпись — распознавать заранее настроенную область даты/времени.
   Для однотипного шрифта рассмотреть лёгкое распознавание цифр/шаблоны, для разных
   надписей — компактный OCR. Выбор проверить на реальных ночных и дневных кадрах.
3. Сопоставлять несколько наблюдений: допустимая дата, диапазон времени, порядок
   соседних кадров, согласованность с датой записи и заданный часовой пояс камеры.
   Оценка confidence OCR — один признак проверки, не гарантия правильной даты.
4. Строить карту `кадр/PTS → camera_time` с границами непрерывных участков.
   Выборку раз в 0,5–2 секунды рассматривать только как стартовый режим измерений:
   участки скачков и окрестности проходов уточняются чаще, при необходимости покадрово.
5. Внутри проверенного непрерывного участка допустима интерполяция с учётом PTS
   и секундной точности надписи. Через монтажный разрыв интерполяции нет.
6. На истинном разрыве сбросить короткое сопровождение боксов, сохранив память
   личностей в пределах часа реального времени. Отличать этот случай от OCR-ошибки
   и обычного восстановления с checkpoint.
7. Обратный ход часов, неоднозначная дата или непрочитанный критический участок
   дают статус проверки времени. Не подменять их незаметно временем обработки.

Например, если в 00:10 файла камера показывает 06:00, а в 00:11 уже 10:00,
между этими соседними кадрами для правила часа прошли четыре реальных часа.
Человек не должен ошибочно считаться вернувшимся через одну секунду.

В карте времени и событиях нужны источник времени, качество/неопределённость,
версия алгоритма OCR и участок записи. Часовой пояс берётся из карточки камеры:
он не содержится в строке часов на изображении. Переход через полночь внутри файла
не обнуляет часовую память. На границе следующего файла память сбрасывается
согласно уточнённому условию заказчика. Дату смены и календарную дату события
полезно хранить отдельно для будущего согласования выгрузки в 1С.

OCR не восстановит события в вырезанных кадрах. Он восстановит время имеющихся
кадров и поможет корректно применить час к видимым проходам. Надёжность самого
ReID остаётся отдельным предметом проверки.

## Как работает планировщик

Начальная рекомендация — очередь заданий в уже используемой PostgreSQL,
с отдельным сервисом загрузки и фиксированным пулом workers.
1700 задач в день сами по себе не требуют нового брокера: основная нагрузка —
кадры и модели, а не число операций выдачи файлов.

1. Файл загружается во временное имя/объект. После завершения загрузчик публикует
   признак готовности или атомарно переносит файл в готовое имя на той же ФС.
   Одно лишь неизменение размера несколько секунд не доказывает завершения загрузки.
2. Проверяются доступность и целостность, длительность, камера/автобус и дата смены.
   Вычисляется контрольная сумма. Одинаковая загрузка того же содержимого в том же
   контексте не создаёт ещё один оплачиваемый прогон автоматически.
3. В БД создаётся job со ссылкой на файл. Само видео в очередь/БД не помещается.
4. Свободный worker атомарно забирает одну готовую задачу короткой транзакцией
   с `FOR UPDATE SKIP LOCKED`, получает срок владения и номер попытки. Транзакция
   не остаётся открытой на все часы обработки.
5. Worker обрабатывает файл и продлевает владение небольшими heartbeat, например
   раз в 15–30 секунд при начальном сроке владения 2–3 минуты. Значения нужно
   подобрать по замерам; heartbeat не должен включать галерею признаков.
6. При завершении результат публикуется атомарно. Worker берёт следующий файл.
7. Если задач нет, worker блокирующе ждёт уведомления, с редкой контрольной
   проверкой БД. После подключения/переподключения он всегда перечитывает очередь.
8. Сервис восстановления возвращает просроченную попытку в очередь. Повторные
   ошибки имеют ограничение числа попыток и задержку. Повреждённый файл уходит
   на проверку, а не блокирует все остальные записи.

`LISTEN/NOTIFY` используется только для пробуждения. Источник истины — таблица:
уведомление не заменяет сохранённую задачу и восстановление очереди после сбоя.

Состояния: `receiving → validating → queued → running → succeeded`.
Дополнительно: `retry_wait`, `failed`, `cancelled`, `needs_review` для времени/данных.

В дальнейшем можно перейти на Celery/RabbitMQ либо иной брокер, если понадобятся
более сложные очереди и эксплуатационные возможности. Само это не ускорит модель.

## Почему retry не должен удваивать пассажиров

В нынешней реализации event_id создаётся случайным UUID. После отката к старому
состоянию повторно найденный проход может получить другой UUID. Одна уникальность
event_id поэтому не гарантирует отсутствие двойного результата целого перезапуска.

Для архива предлагаются отдельные попытки/версии результата:

- Все промежуточные события принадлежат конкретному `job_run_id`.
- Версия анализа и попытка владения worker — разные сущности. Неизменённый анализ
  допускает восстановление тем же run с новым номером владения; пересчёт новыми
  весами создаёт новый run. Все записи checkpoint и событий проверяют номер владения.
- У задания только одна опубликованная активная версия результата.
- Право публикации проверяется по актуальному номеру владения. Старый «оживший»
  worker не может завершить чужую или уже переданную попытку.
- Попытка публикуется целиком после проверки конца файла, времени и согласованности.
- Повторная обработка новыми весами заменяет выбранную версию вклада задания,
  вместо повторного прибавления всех пассажиров к прежнему суточному итогу.
- Отчёты и CSV читают активные версии. Незавершённые результаты видны как черновые.

Checkpoint содержит границу согласованного с ним набора событий, например номер
последнего завершённого блока. При восстановлении от старого снимка незавершённый
или более новый хвост этой версии не считается подтверждённым и переобрабатывается.
Если восстановление начинается в новом run с середины файла, в него также должен
быть перенесён весь подтверждённый префикс событий, а не только память ID и итоговые
числа. Более простой исходный вариант нового run — повтор с начала файла.
Одна лишь смена run_id не решает согласованность курсора и истории событий.

Нужны `recordings`, `processing_jobs`, `job_runs`, `worker_attempts`, `workers`, `checkpoints`,
`time_maps` и привязка событий/итогов к версии результата. Сейчас этих механизмов
в производственном worker нет; простое параллельное копирование `main.py` их не создаёт.

Переносимость checkpoint требует нового логического ключа: job_id, контрольная
сумма содержимого и версии анализа/временной карты. Нынешний configuration_key
включает локальный путь, размер и mtime файла; такой ключ нельзя без изменений
перенести между разными кешами и серверами. Физический путь скачанной копии не
должен менять личность задания. Изменение этого протокола — часть реализации очереди.

Инициализацию/миграцию схемы БД нужно вынести в отдельный шаг развёртывания,
а не запускать конкурирующие ALTER TABLE при обработке каждого нового файла.

У задания фиксируется профиль конкретной камеры и версия моделей/политики подсчёта.
Экспериментальный профиль жилетки одной камеры нельзя автоматически применять
ко всем архивам. Смена весов, геометрии или временной карты не должна незаметно
продолжать несовместимое состояние прежнего анализа.

## Файлы, сеть и хранение

Записи должны быть доступны любому назначенному worker: общее объектное/сетевое
хранилище плюс ограниченный локальный NVMe-кеш. Рабочее место пользователя и
локальный путь на чужом сервере не являются общим источником для всего пула.

Размеры двух текущих файлов: 954 582 817 и 937 375 658 байт, то есть около 0,94–0,95 ГБ.
Если будущие файлы будут похожего размера, при 1700 файлах получится примерно
**1,61 ТБ входного видео в день**, в среднем около **149 Мбит/с только на приём**.
Канал 100 Мбит/с теоретически переносит максимум 1,08 ТБ за сутки без накладных
расходов. На этой оценке он уже не покрывает поступление архива.

Семь суток такого исходного видео — около 11,26 ТБ, без копий, временных файлов
и резервирования. Это оценка по двум файлам, не измеренная средняя всего архива.
При передаче файла каждому worker повторно нужно учесть и внутреннюю сеть.

Задания без работы почти не используют CPU, но остановка обработки и прекращение
расходов на арендованный узел — разные действия. Автомасштабирование должно отдельно
управлять пулом вычислительных узлов по правилам провайдера. Для ежедневной нагрузки
сначала выгоднее измерить устойчивый базовый пул и размер резерва, затем добавлять
полное выключение простаивающих GPU с учётом времени их запуска и доступности.

## Порядок внедрения

1. Создать надёжную очередь на PostgreSQL и приём только завершённых файлов.
2. Добавить изоляцию попыток/результатов, аренду задачи, heartbeat, повтор и отмену.
   Начать с 2–4 workers для функциональных проверок, а не с 1700 процессов.
3. Сделать карту времени по нескольким архивам и проверить монтажные разрывы,
   полночь, закрытые часы и ошибки распознавания. Затем подключить её к счётчику.
4. Реализовать архивное сохранение блоков и проверить сбой процесса/узла без
   потери и удвоения опубликованных пассажиров.
5. Замерить один GPU на настоящих записях с полным конвейером. Сравнить несколько
   одновременно обрабатываемых файлов, батчи, FP16 и исходный режим.
6. На отложенных размеченных эпизодах сравнить детектор, пропуск кадров и фильтр
   персонала. Нельзя уменьшать вычисления ценой необнаруженных быстрых проходов.
7. Рассчитать число узлов, сеть и хранение по измерению. Провести суточный тест
   с искусственным завершением worker, повторной загрузкой и несколькими ошибочными
   файлами. Проверить, что очередь не растёт изо дня в день.
8. Добавить в кабинет очередь, прогресс по файлам, ETA, отставание от дедлайна,
   качество времени, повтор/отмену и версии результатов. Затем согласовать обмен 1С.

Ключевые эксплуатационные показатели: часов видео поступило/обработано, отставание
очереди в часах видео, полезная скорость полного узла, ожидание задачи, срок до
дедлайна, качество временной карты, число повторных попыток и стоимость обработки
одного часа исходного видео. FPS одного YOLO-запуска для выбора размера пула недостаточно.
