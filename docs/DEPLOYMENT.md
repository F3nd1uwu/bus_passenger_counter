# Запуск и эксплуатация

## Файлы и настройки

Для сервера используйте ветку `server`: она включает три рабочие ONNX-модели
профиля `test2`, а её Docker-образ по умолчанию запускает этот профиль. Полная версия
`diploma` включает также исторические и экспериментальные веса для исследований.
Видео и настройки источника нужно предоставить отдельно.
`python -m tools.setup_env` создаёт `.env` со случайным паролем, не перезаписывая
существующий файл. `.env` не публикуется и автоматически читается **Docker Compose**.
При обычном запуске Python настройки берутся из переменных процесса и CLI,
загрузки `.env` приложением нет.

Новый `.env.example` использует проверенный кандидат `person_manual_v1.onnx`,
confidence 0,35 и similarity 0,70. Встроенный профиль `Settings()` остаётся базовым
YOLO26n с 0,10 / 0,50 для совместимости. Существующая `.env` не переключается автоматически.

Основные настройки:

| Параметр | Что задать |
| --- | --- |
| `VIDEO_SOURCE` | Путь к файлу, RTSP/HTTP URL или номер USB-камеры |
| `SOURCE_KIND` | `file`, `stream`, `camera` или `auto` |
| `VIDEO_START` | Реальное ISO 8601 время первого кадра файла с часовым поясом |
| `BUS_ID`, `CAMERA_ID` | Стабильные имена автобуса и двери, 1–32 символа |
| `TIMEZONE` | Часовой пояс суточной статистики |
| `MODEL_PATH`, `REID_MODEL_PATH` | Проверенный детектор и энкодер ReID |
| `CONFIDENCE` | 0,35 для кандидата; 0,10 для базового профиля |
| `TRACKER_IDENTITY_MIN_SIMILARITY` | 0,70 для кандидата; 0,50 для базового профиля |
| `STAFF_MODE` | В общем профиле `disabled`; `--profile test2` включает модель конкретной жилетки v3 |
| `CHILD_MODE` | `disabled`; эксперимент не показал исключений детей на проверенном видео |
| `Y_STREET`, `Y_CABIN`, `DOOR_X_MIN/MAX` | Зоны именно вашей камеры |
| `DUPLICATE_INTERVAL_SEC` | По умолчанию 3600, независимо по IN и OUT |
| `STATE_PATH` | Отдельный постоянный файл состояния для процесса |

Для ускоренного/склеенного архива часы в изображении могут отличаться от PTS.
Приложение не распознаёт часы на изображении: установка `VIDEO_START` исправит
только начало, но не вырезанные промежутки. Для честного часа нужна исходная временная
шкала или отдельная карта временных меток. Тестовый `evaluate_clip` использует
синтетическую дату и не является подтверждением правильной даты посадки.

## Полный Docker-запуск

```bash
python -m tools.setup_env
# Отредактируйте .env: источник, время файла и зоны
docker compose config --quiet
docker compose up --build -d
docker compose ps -a
docker compose logs -f counter_service
```

Эти команды в полной ветке используют настройки `.env` и стандартный Docker CMD.
Для полного репозитория и камеры `test2` добавьте отдельный Compose override:

```yaml
services:
  counter_service:
    command: ["python", "main.py", "--profile", "test2"]
```

Сохраните как `compose.test2.yml` и запускайте
`docker compose -f docker-compose.yml -f compose.test2.yml up --build -d`.
В серверной ветке профиль уже задан в Docker CMD, override не нужен. Параметры
моделей и геометрии `test2` имеют приоритет над одноимёнными переменными `.env`;
адаптацию к другой камере выполняйте отдельным проверенным профилем или CLI.

Для файла: `SOURCE_KIND=file`, `VIDEO_SOURCE=/app/data/test.mp4`, верный `VIDEO_START`.
Для сети: `SOURCE_KIND=stream`, реальный URL и пустой `VIDEO_START`.
Контейнеру нужен сетевой доступ к камере. `localhost` внутри контейнера обозначает
сам контейнер; доступ к хосту/локальной сети настраивается согласно месту камеры.
URL с паролем храните только в приватной `.env`.

USB-камера для Docker на Linux требует проброса устройства через свой Compose override,
например `devices: ["/dev/video0:/dev/video0"]`, и прав на устройство.
На Windows проще сначала проверить USB-камеру нативно через `test_local.py`.

Остановка с сохранением данных:

```bash
docker compose stop counter_service
docker compose stop postgres
```

Повторный запуск: `docker compose up -d`. Завершившийся файл повторно не обрабатывается.
Если файл/модели/пороги изменены, сначала спланируйте отдельное состояние или миграцию.
Не удаляйте рабочие тома и контрольные точки ради повторного запуска.

## Локальное приложение и PostgreSQL в Docker

Для предпросмотра PostgreSQL не нужна. Если нужен именно `main.py` на хосте:

```bash
python -m tools.setup_env
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d postgres
```

Override публикует БД только на `127.0.0.1:5432`. На Windows задайте пароль из
своей `.env` в окружении, а не в исходном коде:

```powershell
$env:DB_HOST = '127.0.0.1'
$env:DB_PORT = '5432'
$env:DB_NAME = 'bus_analytics'
$env:DB_USER = 'bus_counter'
$env:DB_PASS = 'ваш пароль из .env'
$env:STATE_PATH = 'data/local_runtime.sqlite3'
.\.venv\Scripts\python.exe main.py --source data/test.mp4 --source-kind file --video-start 2026-11-01T05:40:00+04:00 --model models/candidates/person_manual_v1.onnx --confidence 0.35 --association-similarity 0.70
```

Время в команде — пример, замените фактическим. Для другого автобуса/камеры задайте
также `BUS_ID`/`CAMERA_ID`. Не запускайте два счётчика над одним источником и одним
локальным состоянием.

## Просмотр статистики

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

```sql
SELECT traffic_date, bus_id, total_passengers AS counted_in, total_out
FROM daily_passenger_traffic
ORDER BY traffic_date DESC, bus_id;

SELECT * FROM current_day_passenger_traffic
WHERE traffic_date = (CURRENT_TIMESTAMP AT TIME ZONE 'Europe/Saratov')::date;

SELECT event_type, counted, reason, COUNT(*)
FROM raw_passenger_events
GROUP BY event_type, counted, reason;
```

Для иного `TIMEZONE` измените часовой пояс в запросе текущего дня.
События с `counted=false` полезны для разбора повторов, персонала и недостатка признаков.

## Арендованный сервер

- Сначала проверьте модель на локальном фрагменте и измерьте скорость на целевом сервере
  с нужным числом камер. Один процесс обслуживает одну камеру/дверь.
- CPU-образ использует CPU PyTorch и ONNX Runtime. Замена `DEVICE` сама по себе не
  добавляет GPU: нужны совместимый runtime, драйверы/проброс GPU и другой профиль.
  Текущий ONNX-энкодер ReID работает на CPU и отклоняет CUDA-конфигурацию.
- PostgreSQL в основном Compose доступен только сервисам его сети. Локальный override
  нужен только для запуска приложения на хосте, на сервере он обычно не требуется.
- Контейнер счётчика непривилегированный; модели и `data` доступны только для чтения.
  SQLite расположен в writable-томе `counter_state`; база — в `pgdata`.
- Следите за местом, свежестью кадров, ростом локальной очереди, доступностью камеры
  и причинами исключения событий. Наличие живого процесса не доказывает наличие кадров.
- Храните резервные копии БД, локальной контрольной точки и конфигурации согласованно.
  Для согласованной копии SQLite остановите счётчик или используйте SQLite backup API;
  копировать только основной файл работающей WAL-базы недостаточно.

Схема обновляется аддитивно при инициализации клиента БД. Сначала сохраняйте резервную
копию и проверяйте обновление на отдельной БД. Защита повторной доставки не заменяет
резервное копирование и не восстанавливает отсутствующие кадры камеры.

## Что проверено перед полевым тестом

14 ноября 2026 отдельно проверены транзакции настоящей одноразовой PostgreSQL,
повторная доставка, восстановление посреди прохода и сохранение локальной очереди
при недоступной БД: 18 инфраструктурных тестов прошли. Зависимости и Compose
прошли проверку. Это не подтверждает скорость и качество на арендованном сервере.
Актуальный [протокол публикации](../reports/release-2026-11-14/README.md).

Начинайте с одной камеры и сравнения событий с ручным подсчётом. Проверьте несколько
смен, переподключение камеры и перезапуск счётчика. Зафиксируйте пропуски, лишние
события и задержку относительно реального времени. Пропускная способность должна
соответствовать потоку; в текущем захвате нет гарантированного удаления старых
кадров ради низкой задержки. Для 60 FPS запас на локальном CPU не показан.
