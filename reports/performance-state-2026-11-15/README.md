# Ускорение сохранения памяти распознавания

Дата: 15 ноября 2026. Изменение затрагивает сохранение состояния и доставку в БД.
Веса, пороги детекции, геометрия двери, признаки ReID и правила подсчёта не менялись.
Работающий арендованный сервер при разработке не обновлялся.

## Что исправлено

- Признаки каждой личности копируются списками вместо рекурсивного обхода каждого
  числа через `dataclasses.asdict`. Снимок по-прежнему независим от дальнейших
  изменений галереи. Поля и значения прежние.
- Для проверки источника и номера версии SQLite читает только заголовок, вместо
  разбора большого JSON предыдущего снимка при каждом сохранении.
- В PostgreSQL передаётся уже сохранённый JSON. Python не создаёт заново сотни
  тысяч float-объектов, чтобы немедленно сериализовать их обратно. Для обновления
  суточных строк SQLite извлекает только дату, автобус и камеру.
- Неизменившаяся, успешно доставленная версия не отправляется повторно той же БД
  в текущем процессе. После перезапуска доставка снова разрешена. Маркер ставится
  только после удалённого commit и локального подтверждения.
- PostgreSQL не переписывает строку памяти при повторе того же номера версии.
  Локальная замена состояния также должна увеличивать версию.

Это оптимизация вычислений и обмена. Частота создания новых контрольных точек,
очередь событий, атомарность сохранения и структура старых JSON не изменены.
Схема PostgreSQL и SQLite не меняется. Действительные прежние снимки читаются
без конвертации; API восстановления `load()` возвращает прежнюю структуру.

## Измерение на синтетическом состоянии

Полные числа: [до](baseline.json) и [после](optimized.json).
Общий сценарий: 128 личностей, признаки по 512 координат, восемь дополнительных
ракурсов на личность. Фиксированное зерно 41, состояние 12 407 208 байт с оболочкой.
Три измерения каждого этапа; ниже указаны медианы. PostgreSQL 16 запущена в отдельном
локальном тестовом контейнере. Сравнение выполнено последовательно, без параллельных
видео-тестов во время замеров. Это локальный Windows-стенд, не арендованный сервер.

- Создание снимка: **71,97 → 7,49 мс**, ускорение примерно **9,6 раза**.
- Сохранение в SQLite: **671,18 → 413,86 мс**, примерно **1,62 раза**.
- Доставка изменившегося снимка в PostgreSQL: **1 528,62 → 709,33 мс**,
  примерно **2,16 раза**. Подготовка очередного снимка и его локальное сохранение
  в это измерение доставки не входят.
- Пять синхронизаций без изменения: **7,53 с → 0,23 мс**. Раньше повторно
  передавались пять снимков — около **65 МБ JSON**, с приростом WAL около **40,6 МБ**.
  После изменения: **0 отправок, 0 байт JSON и 0 байт дополнительного WAL** в этом
  изолированном тесте. Это случай отсутствия изменений, не оценка всего сетевого
  трафика при непрерывной обработке.

SHA-256 канонического состояния движка до/после одинаков:
`332c060511bd110add4f0a1f9db042db2abf8364ea11ad254b7a118c9bcf43f4`.
Проверено точное восстановление после SQLite и PostgreSQL, включая все float-значения.
Ни уменьшение размерности, ни округление, ни сжатие с потерями не используются.

Из этих цифр нельзя вывести FPS всей программы или обещать уменьшение суточного
прогона в 2,16 раза. В реальном процессе остаются детектор, ReID, сопровождение,
чтение видео и создание новых снимков. Ускорен измеренный участок обработки.
Нужен повторный серверный замер на одинаковом фрагменте и при одинаковой нагрузке.

## Проверки корректности

Основной прогон: **180 тестов, ошибок и пропусков нет**, 159,30 с.
Включены приватные видео-регрессии, повторные проходы, ReID, жилетка,
восстановление и отдельная PostgreSQL. Новые проверки включают:

- повтор неизменной версии и отправку в другую БД;
- отправку следующей версии после простоя;
- сбой PostgreSQL и потерю локального подтверждения;
- повторную доставку после перезапуска;
- очередь из 501 события: снимок не обгоняет недоставленные события;
- неизменность номера транзакции и времени PostgreSQL при повторе версии;
- независимость признаков в снимке и точное совпадение с прежним форматом.

После дополнительной защиты явного номера версии отдельно выполнены **11 проверок
SQLite и обновления старого состояния**, без ошибок. Среди них новый сценарий
отказа от замены версии 5 версией 5 или 4. Дополнительно проверено восстановление
файла после сбоя между редкими контрольными точками. В текущем наборе 182 теста.
В Linux-контейнере Python 3.12 отдельно проверены блокировка SQLite, json_extract,
оба способа доставки и точное восстановление из PostgreSQL. Все 25 веб-тестов
также пройдены.

## Дополнительная настройка для архивных файлов

Для нового теста **файлов** можно задать `CHECKPOINT_INTERVAL_SEC=10` в окружении
обработчика. Периодические снимки тогда создаются раз в десять секунд времени
видео. События по-прежнему сохраняются немедленно вместе с актуальным снимком.
При сбое несохранённый участок файла перечитывается с последней контрольной
точки; это отдельно проверено искусственным сбоем посреди прохода.

Для прямой камеры такая потеря промежуточного состояния может затронуть проход
в момент сбоя: старые кадры не всегда можно получить снова. Поэтому интервал
камеры автоматически не увеличивался, базовое значение осталось 1 секунда.
Изменение интервала не восстанавливает реальную временную шкалу смонтированного
файла и не улучшает часовое узнавание. Ускорение всего видео при интервале 10 с
в приведённые выше измерения не входит: его ещё нужно замерить на сервере.

## Воспроизведение

Только отдельная тестовая PostgreSQL с учётными данными существующего тестового
протокола. `--postgres-port` не должен указывать на рабочую БД.

```bash
git worktree add --detach .local/performance-baseline e134839
python -m tools.benchmark_persistence --code-root .local/performance-baseline --postgres-port 55440 --output .local/baseline.json
python -m tools.benchmark_persistence --postgres-port 55440 --output .local/optimized.json
```

Без `--postgres-port` измеряются только снимок и локальное сохранение. Исходные
ролики и модели для этого инструмента не нужны. Уникальные тестовые строки
удаляются после замера. База и секреты из `.env` инструментом не читаются.
JSON результата фиксирует базовый коммит, хеш изменений core/database и хеш
общего инструмента измерения. Оптимизированный замер выполнен в рабочем дереве
поверх того же базового коммита; сохранённый diff-хеш отличает две реализации.

## Что остаётся по качеству

Сохранение старых контрольных итогов означает отсутствие обнаруженной регрессии,
а не рост точности. В частности, прежний контроль первого видео сохраняет известный
учтённый вход водителя без жилетки. Этот случай не объявлен исправленным.

Просмотрены кадры 12 событий STAFF из полного первого прогона. В них встречается
обычная верхняя одежда без видимой рабочей жилетки. Это отдельные кандидаты на
ошибочное исключение: по одному кадру нельзя установить, была ли причина в
модели жилетки или в переносе ранее подтверждённой метки через ошибку ID.
Поэтому такие случаи проверяются на последовательностях кадров, а не объявляются
новой точностью фильтра по одиночным изображениям.

### Дополнительная проверка фильтра жилетки

Для трёх таких входов первого видео заново получены сырые детекции и признаки,
затем последовательности воспроизведены с новым трекером и пустой памятью.
Исходная модель v3 снова дала STAFF на тех же кадрах перехода:

- N01: кадр **81 396**, обычная светлая куртка;
- N06: кадр **228 431**, обычная верхняя одежда;
- N10: кадр **342 783**, стёганая куртка.

Так воспроизведены ошибочные решения на коротких последовательностях без
наследования состояния из предыдущих часов полного прогона. Накопленная большая
память первого запуска для появления этих ошибок не требуется.

Проверен кандидат: пространственное согласие существующих моделей жилетки v2 и v3,
порог совпадения боксов IoU 0,3. Он сохранил прежние три исключения водителя V01,
V03 и V05, но **не исправил ни одного из трёх выбранных ложных STAFF**.
Кандидат отклонён, дополнительные модели в рабочую конфигурацию не включены.
[Структурированные результаты](staff_diagnostic.json).

Подъём одного порога также не разделяет эти примеры при прежних двух
последовательных подтверждениях. Для положительного V03 максимальный минимум
соседней пары оценок — **0,2003**. Для отрицательного N06 он достигает **0,4870**.
Сохранить V03 требует порога не выше 0,2003; убрать N06 — выше 0,4870.
Оценки детектора не являются калиброванными вероятностями принадлежности персоналу.
Это анализ записанных последовательностей, а не подбор нового рабочего порога.

Следовательно, прежняя проверка жилетки на коротких контрольных эпизодах была
недостаточной для полного первого видео. Нужна отдельная доработка модели жилетки
на таких отрицательных примерах и проверка на отложенных сценах. Водитель без
жилетки дополнительно требует подтверждённой связи его проходов, а не только
детекции одежды. Детектор людей этими экспериментами не переобучался.

Около 260 пассажиров и 38 проходов водителя — приблизительные оценки с неуточнёнными
направлениями. Они не используются как цель для подгонки порогов. Следующие проверки:

1. Отдельно разметить проходы водителя в COUNTED и решения STAFF: сколько настоящих
   работников исключено и сколько пассажиров исключено ошибочно.
2. Проверить связь того же человека между несколькими проходами, а не только
   совпадение IN/OUT. Выдать новый ID легко, восстановить верную личность сложнее.
3. Использовать непрерывную запись или временную карту монтажа: в имеющемся файле
   час PTS не соответствует реальному часу камеры. Одна замена VIDEO_START
   не исправляет вырезанные промежутки.
4. После этого сравнивать варианты весов и настроек на отложенных эпизодах.
   Повторное обучение детектора людей не решает автоматически фильтрацию водителя,
   потерю ID и нагрузку от сохранения памяти.

Документация используемых операций: [SQLite json_extract](https://www.sqlite.org/json1.html#jex)
и [PostgreSQL INSERT ON CONFLICT](https://www.postgresql.org/docs/16/sql-insert.html).
